# ADR-0019: License and versioning

- **Status:** Accepted
- **Date:** 2026-11-26

## Context

The core is published as a public npm package (`@edgonzalez24/nuxt-keel`, ADR-0001). It needs a clear license, a versioning policy, and a release process that keeps the changelog accurate and reduces manual steps.

The MIT license file was already committed (`fc72216`).

## Decision

**License:** MIT. Already in the repository. All dependencies must have MIT, Apache 2.0, BSD, or ISC licenses (AGENTS.md).

**Release tooling:** Changesets. `pnpm changeset` describes a change; the Changesets GitHub Action automates the rest.

**Release workflow:**

1. When a change affects the public API or behavior of the layer, the developer (or agent) runs `pnpm changeset` and commits the generated `.changeset/` file alongside the code change.
2. When one or more changesets land on `main`, the Changesets GitHub Action opens (or updates) a "Version Packages" pull request that includes the bumped version in `package.json` and the generated `CHANGELOG.md` entries.
3. Merging the "Version Packages" PR triggers CI to publish to npm and create a GitHub Release with the same changelog content.

No manual tagging. No manual `npm publish`. The only human action after the initial changeset is merging the Version Packages PR.

**Changelog:** `CHANGELOG.md` at the monorepo root (generated by Changesets) + GitHub Releases (populated by the Changesets GitHub Action).

**Versioning policy:**

*Pre-1.0 (current):*
- The package is `0.x`. No semver stability guarantees. Any release may contain breaking changes.
- Use `patch` for bugfixes and small additions, `minor` for meaningful new features. Do not use `major` until the 1.0 decision.
- Every release documents what changed in the changeset description.

*Post-1.0:*
- Full semver. The following changes require a **major** bump:
  - Removing or renaming a module option (e.g., `storageAdapter` → `storage.adapter`).
  - Removing or renaming a field in `ServiceContext`.
  - Removing or renaming a type or function from the package's public exports.
  - Changing the behavior of an existing feature in a way that requires app code changes.
  - Removing or renaming a route the layer exposes (e.g., `/api/health`, `/api/storage/:key`).
- The following are **not** breaking, even if significant:
  - Adding optional fields to `ServiceContext`.
  - Adding new module options with defaults.
  - Adding new public exports.
  - Bugfixes that correct documented incorrect behavior.

## Consequences

- Every meaningful change ships with a human-readable description in the changelog — no silent updates.
- The release process has zero manual steps beyond merging the Version Packages PR.
- Consumers of the package can read `CHANGELOG.md` in the repo or the GitHub Release to understand what changed without leaving GitHub.
- Pre-1.0 consumers are explicitly warned that breaking changes can appear in any `0.x` release.

## Rules for agents

- Any change to the public API, module options, `ServiceContext` shape, exported types, or layer routes must be accompanied by a `.changeset/` file created with `pnpm changeset`.
- Never run `npm publish` or push an npm tag manually — the release process is always via the Changesets Action.
- Pre-1.0: use `patch` or `minor` for all changesets, never `major`.
- Do not merge the "Version Packages" PR without human approval — it triggers a public npm publish.
- Dependencies added to the core must have MIT, Apache 2.0, BSD, or ISC licenses. Verify before adding.
