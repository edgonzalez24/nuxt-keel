# ADR-0007: Auth and sessions

- **Status:** Accepted
- **Date:** 2026-11-26

## Context

The core uses Better Auth for authentication and session management. Before writing any auth configuration, we need to settle session lifetime, cookie policy, email verification enforcement, which OAuth providers ship by default, and how optional features (organizations, 2FA) are handled.

Constraints:
- Better Auth is the auth library (established by the stack).
- Session cookies are managed by Better Auth — the core does not create its own (AGENTS.md security rule).
- Email is sent via Resend (established by the stack).
- Auth configuration is a human-approval area (AGENTS.md).

## Options considered

**Session lifetime:**
1. 30-day sliding window (renewed on activity). Standard "stay logged in" behavior.
2. 7-day fixed. More conservative; users re-authenticate weekly.
3. Configurable via module options with a 30-day default.

**Email verification enforcement:**
1. Required — Better Auth middleware rejects unverified sessions on all routes except `/api/auth/**`. Services assume a valid session implies a verified email.
2. Optional — the core sends the verification email but does not block access. Apps decide enforcement.
3. Optional with a module flag (`requireEmailVerification: true`).

**OAuth providers:**
1. None by default — apps opt in per provider via module options. Email/password always active.
2. GitHub + Google by default — most common providers, but forces those dependencies on all apps.

**Organizations plugin:**
1. Off by default — enabled with `enableOrganizations: true` in module options.
2. Always on — adds member/invitation tables to every app unconditionally.

**Session revocation:**
1. GraphQL mutation `signOutAllDevices` in the core + automatic revocation on password change.
2. REST endpoint from Better Auth only (`/api/auth/revoke-sessions`).

## Decision

**Session lifetime:** 30-day sliding window as the default. The module option `sessionExpiresIn` overrides it. Sessions are renewed on each authenticated request (`updateAge` = 1 day — the session TTL is extended if more than 1 day has passed since the last renewal).

**Cookie attributes:** Fixed — not configurable.
- `HttpOnly: true`
- `Secure: true`
- `SameSite: lax` (permits cross-site GET navigation required for OAuth redirects)

**Email verification:** Required. Better Auth middleware rejects sessions of unverified users on all routes except `/api/auth/**`. Services receive a verified user or `null` — they never check `emailVerified` manually.

**OAuth providers:** None in the core's base configuration. Apps declare the providers they need in module options (`oauthProviders: ['github', 'google']`). Credentials go in `runtimeConfig`. The core wires the providers into Better Auth when the option is set.

**Organizations plugin:** Off by default. Enabled with `enableOrganizations: true` in module options. The plugin's additional tables are only created when the option is active.

**Session revocation:**
- GraphQL mutation `signOutAllDevices: Boolean!` in the core schema.
- Automatic revocation of all sessions when the user changes their password.

**Out of scope for the core** (apps enable via Better Auth configuration if needed): two-factor authentication, magic links, passkeys, social login beyond the declared providers.

## Consequences

- Services never check `user.emailVerified`. A valid session always means a verified user.
- The client uses only GraphQL for auth operations — no mixed GraphQL + REST calls for auth.
- Apps with OAuth configure credentials in `runtimeConfig` and declare providers in module options. The core handles the wiring.
- The base schema does not include organization tables. They appear only when the option is active, keeping the default data model minimal.
- Cookie attributes are fixed for security. Any attempt to relax them requires an ADR amendment and human approval.
- Changing session duration, adding OAuth providers, or enabling organizations are module-option changes, not code changes in the layer.

## Rules for agents

- Never modify cookie attributes (`HttpOnly`, `Secure`, `SameSite`). These are fixed security settings — relaxing them requires human approval (AGENTS.md).
- Do not check `user.emailVerified` in services or resolvers. Enforcement is at the middleware layer.
- Never add an OAuth provider to the core's base configuration. Providers are opt-in via module options; credentials go in `runtimeConfig`.
- The `signOutAllDevices` mutation must revoke all sessions for the authenticated user. Password changes must trigger the same revocation automatically.
- The organizations plugin registers only when `enableOrganizations: true` is set. Do not add organization-related tables or resolvers to the base schema.
- 2FA, magic links, and passkeys are out of core scope. Do not add them without an ADR amendment.
